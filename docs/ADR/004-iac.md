# ADR-004: Infrastructure as Code — Terraform

## Status

In review

## Context

Project Atmos is designed as a production-oriented DevOps project with a focus on reliable application delivery, Kubernetes operations, CI/CD, observability, and reproducible deployments.

The project runs in a cloud Kubernetes environment. Infrastructure as Code could be introduced to provision and manage cloud resources such as the Kubernetes cluster, networking, storage, and related infrastructure.

Terraform is a common approach for managing such infrastructure through declarative configuration and version-controlled code.

The decision is whether introducing Terraform provides enough additional efficiency, control, and operational value for the current project scope to justify the additional complexity.

## Options considered

### 1. Terraform

Use Terraform to provision and manage the cloud infrastructure required by Project Atmos.

Advantages:

- Infrastructure is defined as code.
- Cloud resources can be provisioned and changed in a reproducible way.
- Infrastructure changes can be reviewed through Git.
- Terraform provides a declarative and version-controlled management layer for cloud resources.

Trade-offs:

- Adds another infrastructure management layer to the project.
- Requires Terraform configuration, state management, providers, variables, modules, and credentials.
- Increases operational and maintenance complexity.
- A significant part of the project effort would shift from application delivery and Kubernetes operations toward infrastructure provisioning.

### 2. Manual cloud infrastructure provisioning

Create and configure the required cloud resources directly through the cloud provider.

Advantages:

- Minimal additional tooling and operational overhead.
- No Terraform state or configuration to maintain.

Trade-offs:

- Infrastructure changes are less reproducible.
- Less infrastructure configuration is represented in Git.
- Manual changes are harder to review and audit.

### 3. Terraform for the entire application platform

Use Terraform not only for cloud infrastructure but also to manage a significant part of the Kubernetes application platform.

Advantages:

- A single IaC tool could manage multiple infrastructure layers.
- Infrastructure and platform configuration could be controlled through code.

Trade-offs:

- Creates overlap between Terraform and Kubernetes-native configuration.
- Adds additional abstraction around resources already managed effectively by Kubernetes and Kustomize.
- Increases configuration and operational complexity.

## Decision

Terraform is not included in the current Project Atmos architecture.

Cloud infrastructure required for the project will be provisioned separately, while Kubernetes resources and application environments will be managed using Kubernetes manifests and Kustomize.

This is a deliberate scope and architecture decision rather than a technical limitation.

## Why

Terraform provides clear benefits for infrastructure provisioning and lifecycle management. However, for the current Project Atmos architecture, these benefits do not provide sufficient additional efficiency and operational control to justify introducing another infrastructure management layer.

The project already contains several significant DevOps components:

- Docker and Docker Compose;
- Kubernetes;
- Kustomize;
- Ingress;
- cloud Kubernetes;
- GitHub Actions;
- Docker Hub;
- MongoDB and Redis;
- credential rotation;
- Prometheus;
- Grafana;
- Loki.

Adding Terraform would increase the number of technologies and operational layers without providing a proportionate improvement to the application's deployment workflow.

Kustomize already provides the required mechanism for managing Kubernetes resources across `dev` and `prod` environments.

Therefore, cloud infrastructure provisioning and Kubernetes application configuration remain separate concerns. Kubernetes resources and environment-specific configuration are managed through Kubernetes manifests and Kustomize.

## Consequences

### Positive

- Smaller and more focused architecture.
- Less infrastructure configuration to maintain.
- No Terraform state management.
- No additional Terraform-specific CI/CD workflow.
- Kubernetes deployment remains centered around Kubernetes-native resources and Kustomize.
- Keeps the operational model focused on Kubernetes-native deployment, CI/CD, security, observability, and reliability.

### Trade-offs

- Cloud infrastructure is not fully represented as Terraform code.
- Infrastructure changes are less reproducible than with a complete IaC approach.
- Cloud resources are managed outside the project's Kubernetes deployment configuration.
- The project does not demonstrate Terraform-based infrastructure lifecycle management.

## Scope Boundary

Terraform is intentionally outside the current Project Atmos scope.

The absence of Terraform does not mean Infrastructure as Code is considered unnecessary in general. It means that introducing Terraform into this architecture does not provide sufficient additional value for the current requirements to justify its complexity.
